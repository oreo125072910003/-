# 微信识图清晰度修复

用户反馈：图片发给小助手后，经常被回复看不清。

当前部署状态（2026-10-28 13:30）：统一发布已将本记录的最终多图与局部容错源码纳入实际运行桌面 1.0.5 和完整插件候选 1.1.3；相关桌面归档源码及实际运行目录的三个 Python 读取文件均与主工程一致。详见 `20261028_客户端控制与新邮件通知.md` 的本机安装审计。普通新微信图片的完整接收与回答仍未专门验收；下文“尚未部署”仅描述当时交接状态。

## 已确认的原因

普通来图复用了表情预览归一化：无论是照片还是长截图，都先把长边缩到 1280 像素，再以 JPEG 保存。1080×6000 的截图实际只剩 230×1280，小字在进入 DSH 以前已经丢失。图片解析还会返回第一个可解码的本地副本，可能先命中同条消息的缩略图；旧预览缓存会持续沿用。

## 实现

- 普通图片匹配当前 DSH 原生附件的 2048² 像素和 8192 长边预算；小图不放大。截图优先无损 PNG，照片在必要时使用 JPEG 并逐步调整，维持原有单张 768 KiB 上限。正确处理 EXIF 方向和透明背景。
- 仅在原消息资源 ID 对应的本地副本中比较有效分辨率，保留损坏副本的回退；不会跨消息猜图。
- 超过 2400 像素且长宽比至少 2.5 的图，生成最多三张有重叠的局部图，覆盖全部长边。模型同时收到总览和局部原生图片。单轮仍最多四张，多个来源之间预留总览并分享局部图名额；普通小图不额外分图。
- 读取响应相应设为有界的 5 MiB。每个局部仍校验格式、字节数、SHA256、消息绑定和原图内坐标；宿主任务正文和四图上限保持原契约。
- 总览与实际使用的局部图均快照到任务资料，保留坐标和摘要。提示明确哪些画面已经提供、是否只有缩略图，并要求用局部图核对小字、不要重复统计重叠内容，也不要猜填数字和型号。
- 缓存标识升级为 `readable-v3`；旧预览重新生成，仅有缩略图时后续读取仍尝试更完整的本地副本。表情预览保留原有预算。

## 多图与局部容错补充（2026-10-28，尚未部署）

继续检查发现，先前按来图数量即时分配局部名额，会给没有局部图的普通图片预留无用名额；局部图又固定从第一张开始截取，多张长图容易只提供顶部。此外，桥接层会因任一局部坐标或内容校验失败而拒绝有效总览。

- 改为先读取每张可用总览，再把四图预算中的剩余名额轮流分配给确有有效局部图的来源。普通图与失败总览不占用局部名额。例如一张长图加一张普通图，现在提供两个总览加长图的两端局部；两张长图各提供总览及中部局部。
- 按原图长轴和坐标选局部：一个名额优先中部，两个名额取两端，足够时提供全部。横向长图和乱序局部也适用。这是有界分配策略，没有新增模型调用，也没有把单个局部当成整图精读的证据。
- 桥接层逐个验证局部的字节、SHA256 和原图内坐标。坏局部被排除，后续好局部继续验证；列表格式错误、超过三张或缺少可信源图尺寸时，局部不可用，仍保留通过原会话绑定和摘要验证的总览。只向任务传递布尔故障标记，不传入读取器的自由文本。
- 任务层再次独立验证局部，保留成功画面。微信图片读取记录、资料读取记录和附件状态均记录实际快照的名称、摘要、大小、坐标，以及可用/提供/省略数量和故障标记，不包含图片 Base64。
- 预算不足或局部失败时，提示明确哪些画面未提供，不能声称已核对其中的小字。三张或四张长图仍受四图上限约束，无法保证每张都提供完整高清局部。
- 取消读取后保留已取得总览和读取记录，未取得的局部记为省略；迟到的读取结果不能启动模型或写入图片快照。
