# 小助手 0.3 开发与验收记录

记录日期：2026 年 10 月 25 日。对应源码版本：0.3.0。

这一轮已经把小助手推进到“有分类桌面、通信入口、任务记录和实际文件成果”的阶段。她仍在开发中，不能把界面上有入口、代码测试通过，理解为所有真实账号和工作场景都已验收。

**永久原则：小助手的核心始终是 DSH，默认复用现有 Harness 的登录和模型。** 她有独立的程序窗口、名字、人格、任务和产品数据；其他 API、模型和 agent 是她可以使用的辅助能力。保存额外 API 密钥不会切换或替代这个核心，也不要求为了小助手再登录一套模型账户。

本记录补充前期开发计划和 0.1 预览版记录。旧记录中的“尚未接入”应结合下面的最新进展阅读；完整任务书仍须逐项验收，没有全部完成。

## 现在打开界面，应当能看懂怎样使用

桌面整体改成经典 Windows XP 风格：蓝色标题栏、传统按钮、资源管理器式侧栏和分类标签。主要入口按用途组织，不把所有设置堆在工作台。

| 入口 | 用来做什么 |
| --- | --- |
| 工作台 | 描述要做的工作、添加资料、发起任务 |
| 任务记录 | 看进度、失败原因、工作记录和已经保存的成果 |
| 协作帮手 | 选择写作与审查、双路分析等预设流程 |
| 微信通信 | 看当前微信账号、选择好友和群、查看消息、准备和发送回复 |
| 邮箱通信 | 添加多个邮箱、手动收信、看草稿和发送记录 |
| 能力中心 | 管理工具插件、Skill 工作方法、旧能力迁移和 DSH 授权 |
| 控制面板 | 设置名字、人格，以及检查 DSH 连接 |

微信内部再分“消息与回复”“好友与群聊”“连接设置”；能力中心再分工作能力、插件、技能和原有能力。邮箱把收件、写信和账号配置分开。高级连接参数放在对应设置里，日常操作以名字、会话和工作内容为主。

## 微信：沿用原有工程，逐项迁移

微信以现有 WeChatAgent 源码、身份映射和真实接口为依据，复用原有模块，不靠再启动另一个 WeChatAgent 程序完成整合。迁移范围和差异见 [微信功能迁移对照](../../packages/wechat-bridge/功能迁移对照.md)。

本轮已接入：

- 读取并核对这台电脑当前登录的微信账号，显示本人昵称、微信号等真实资料。当前原生接口缺少本人资料路由时，从原读取服务中精确匹配本人记录；不会把“小助手”的设定名字当成微信账号昵称，也不编造头像。
- 按名称查找好友和群，选择允许小助手读取的聊天；显示会话名称，数字编号只作为辅助信息。更换登录账号后暂停旧账号的收发，重新核对。
- 读取授权会话的最近历史，区分自己发出的消息和收到的消息，并保存到小助手数据库；历史和实时消息使用原协议去重。
- 显示已有图片、表情的安全预览，沿用原表情选择与发送协议。部分动图来自原服务的静态或抽样预览；普通图片发送尚未按完整原协议迁移，不能称为所有媒体能力都已完成。
- 根据来信起草回复；也可在选定会话后主动写文字，不必等待别人先发一条消息。AI 起草不会自动发送。
- 先保存发送记录，再调用原发送接口。只有核对到原数据库的服务器回执，才标记为已送达；结果不明确时保留“未确认”，重复点击和程序重启不会偷偷重发。

当前适配的是已经核对的微信 4.1.10.27 接口，不能承诺任意微信版本通用。历史接口每次最多返回最近 100 条，原接口没有向更早消息翻页的参数；本版没有虚构完整历史分页。原微信的长期记忆、所有扩展玩法与全部媒体能力仍需逐项迁移和验收。

本轮做了本机替身协议和桌面流程验证，并完成真实微信的只读连接：登录账号通过核验，昵称通过原消息读取账号和联系人资料交叉核对取得；25 位联系人和 2 个群均返回名称。**真实微信对外发送尚未验收**，没有用用户账号发送测试消息。

## 原有技能、插件和 DSH 授权

可以清点原有 Skill 与扩展，保留原工作方法、资料和来源。迁移结果逐项显示“已迁入启用”“原有 / DSH 管理”“需要适配”等状态。同名技能保留已有版本；依赖其他宿主、缺少必要工具的技能会留下检查结果，不会一律标成可用。

原生 DSH 插件继续由 DSH 管理。复制文件或看到能力名称，不等于已经实际执行成功。桌面可以读取 Harness 实际提供的技能和工具目录，并由主人逐项勾选允许桌面任务使用的能力。执行前还会核对当前目录与权限；目录不可用时收紧权限。

**微信来信、邮件正文、技能文字和其他助手的输出，都不能替主人授权。** 即使主人已给桌面工作授权，微信和邮件的起草任务也拿不到这份授权。已有本地替身回归同时验证主人直接任务与两种外部来信的差别，没有在测试中真正发信或调用模型。

MCP 可以理解为“接工具的插座”，Skill 可以理解为“一类工作的做法”。目前本机 stdio MCP 支持安装、启停、检测和明确的工具允许清单；不等于开放任意网络插件或让模型随意启动程序。Shell、任意文件操作、插件管理和不受控的再委托等系统控制能力仍有限制。

## 邮件：多账号插件已经实现，兼容性要按邮箱确认

邮箱可以逐个添加，也可以导入账号 JSON 配置。标准 IMAP 用于收信，SMTP 用于发信；每个账号可有自己的服务器、用户名和凭据。密码、专用授权码或已有 OAuth 访问令牌由系统凭据保护保存，不写入普通设置和邮件数据库。

目前收信由你手动触发，只读打开邮箱，不设已读、不移动、不删除服务器邮件。界面使用纯文本正文，不加载邮件中的远程图片。附件先放到独立隔离目录，原文件名不参与磁盘路径；读取时核对它属于哪封邮件，以及大小和文件校验值，不自动打开或执行。

草稿需要先保存，再由你点击发送。SMTP 明确接收后记录“服务器已接收”；这不能证明邮件已进入对方收件箱。连接中断或回执不清楚时记为“未确认”，不会自动再次发送同一草稿。

实际限制包括：

- 邮箱服务商必须开放对应的标准协议，并提供可用授权；不能保证所有邮箱无条件接入。
- OAuth 目前接收已经取得的访问令牌，尚无服务商网页登录授权和自动续期。令牌过期后需要重新授权。
- 每次读取最近 1 至 100 封，不是完整邮箱历史归档；没有后台定时收信和自动发送。
- 单封原文超过 8 MiB 或本次原文预算超过 32 MiB 时只保存元数据；正文有长度上限。每封最多隔离 20 个附件，每个最多 5 MiB，超限会注明。
- POP3、日历、通讯录、复杂自动分类规则和把附件直接发给外部收件人不在这次完成范围。

邮件插件 14 项测试通过，其中包括真实 IMAP/SMTP 客户端库与本机协议替身交互、发送后断线、重启和重复点击。**尚未登录真实邮箱，真实收信与投递仍待验收。** 详细接口见 [邮件插件说明](../../packages/mail-plugin/README.md)。

## 本轮代码审查与修复

独立复核确认并修复了三项集成问题：

1. 发布脚本仍使用旧文件清单，会漏掉新增模块和邮件库的间接依赖，导致打包后无法启动。已补齐产品模块、复用的旧模块和生产依赖；最终安装包已实际启动并通过桌面验收。
2. 协作任务请求取消后，执行器没有确认停止时仍会显示“已取消”。已改为“中断 / 停止待核对”，保留实际状态和已有记录，不接纳迟到结果作为成功成果。
3. 登记任务时等待远端权限清单，退出可能提前关闭数据库，随后登记失败。已把可信发起来源单独保存，将授权核验移到实际执行前，避免这段等待落在任务登记和退出之间；后续协作步骤也会重新核对权限。
4. 已安装的内置合同 MCP 会固定指向旧版程序。升级时现在更新到新包路径、保留版本历史，并取新旧工具和权限清单的交集；默认停用，等待主人重新启用。用户自配的同名插件不会被覆盖。
5. 旧版本保存的 SDK 配置目录可能采用 AppData 的另一条等价路径。生产已固定为 DSH 宿主模式，保存名字和人格时忽略这项旧 SDK 字段，避免它无故阻断保存；禁止切换核心的规则保留。

外部来信不继承主人授权和协作停止未确认的服务回归已加入测试。自动测试没有调用真实邮箱、真实微信发送或收费模型；另单独进行了一次明确标记的真实 DSH 连接验收，见下表。
