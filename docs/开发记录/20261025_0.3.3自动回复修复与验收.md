## 实际故障和修复

真实运行记录显示，多条任务已有 DSH 完整文字和“回答已完成”事件，随后却被产品标成 `interrupted`，没有生成出站记录。根因是原生宿主正常完成也返回 `cancellation:{requested:false,confirmed:false}`，产品仅检查 `confirmed===false`，将没有发生的取消误当成停止未确认。

现在只有确实请求取消或产品本地停止信号已触发，且宿主没有确认停止时，才进入停止待核对状态。普通成功结果会保存答复、绑定持续会话，再交给微信发送。原来被拦住的消息保留原记录，不自动补发。

本轮同时修复：

- 多聊天可以并发生成回复，自动回复的发送阶段串行执行；每条只提交一次。排队到发送前重新检查账号、授权、连接、人工接管、开关和时间预算，失效则不发送。手动发送和其他发送器仍可能占用桥接接口，尚未实现跨所有发送入口的统一队列。
- 连接时间按 reader 的秒精度确定下界，避免丢掉连接后同一秒的新消息。更早整秒和重复入站 ID 继续拦截；reader 只有秒精度，无法分辨握手同秒未见过的历史事件和新事件。
- 附件在桥接接口忙碌、尚未调用媒体传输时，明确报告 `attempted:false`；界面可以显示“未发送”，处理后由主人显式发起新请求。已提交或结果未知的发送仍不会自动重试。
- 协作 worker 保留真实停止未确认状态和并发额度，不能把上游 `CANCEL_UNCONFIRMED` 当普通失败后声称已经停止。正常未取消的成功回执可以释放额度。

## 原生图片研究的独立边界

提交 `d9982d1` 增加受控 `/SendImgMsg` 路由和离线 C++ 探针，9/9 通过。上游中文路径长度处理存在可核实错误，原生对象布局、所有权和投递结果缺乏真实 ABI 证据。因此生产能力明确关闭，请求在读取图片和创建投递账本前返回 `IMAGE_NATIVE_ABI_UNVERIFIED`。

没有部署 DLL、修改旧运行目录或改变当前微信图片发送通道。0.3.3 的图片和文件仍使用原受限 UI 路径，真实投递尚未验收。详见 [原生图片协议验证](../../代码/项目/scripts/native-hook/IMAGE-TRANSPORT.md) 和 [媒体发送说明](../../packages/wechat-bridge/MEDIA-TRANSPORT.md)。

已只读确认 Harness 本身有原生图片附件入口，但产品宿主当前 `images:false`、尚未传递像素。下一步应沿现有 `resolveImage`、原生 attachment 服务与实际模型 modality 检查接线，不能把图片占位文本说成识图，也无需另建核心模型循环或要求另一份核心 API Key。
