## 图片与文件发送路径的实际限制

原 `代码/项目/components/WeChat-Hook/src/SendImageMsg.cpp` 中函数名是 `Route_SendImageMsg`，但注册的 HTTP 路由为 **`POST /SendImgMsg`**；`代码/pcbridge/mcp_dsh_server.py` 使用的也是 `/SendImgMsg`。旧文档把 `SendImageMsg` 写作路由名不准确。当前本机运行的自定义 Hook 对 `/SendImgMsg` 仍返回 404，0.3.1 没有宣称修复该原生路由。

当前替代路径见 [MEDIA-TRANSPORT.md](MEDIA-TRANSPORT.md)：用户先在桌面选择附件，服务消费专用的一次性选择授权，将内容复制为产品数据目录中的快照并保存 SHA256。公共接口只返回附件 ID、名称、大小和摘要，外部聊天文字不能提交任意本地路径。桥接再次核对文件和当前账号、授权及目标映射后，才调用产品自有固定脚本。

UI 路径要求用户已打开目标聊天，能唯一核对联系人、准确窗口标题、空输入框、附件预览名称和发送按钮。没有裸坐标点击、清空已有草稿、盲目回车、失败自动重试或更换媒体类型重发。每个 deliveryId 先落账本，再取得最后一次提交授权；提交一次后仅等回执。窗口 UIAutomation 不可读、重名、焦点变化、缩放、客户端版本和原图行为均可能使该路径无法完成。

界面操作成功不代表送达。送达只接受目标会话中提交后新出现的出站数据库行，核对账号、媒体类型和非零 serverId；图片需 MD5 与源文件精确匹配，文件还需名称、大小和 MD5 全部匹配。图片被微信重新编码、缺完整 XML/摘要或存在多个候选时，保留未知状态，不能据时间变化推断成功。

- `delivered`：已经取得内容匹配的服务器回执。
- `rejected`：仅限可信预提交错误代码且 transport 明确 `attempted === false`，确认未发送；用户处理后可显式重新发送，生成新 requestId，旧记录保留。
- `unconfirmed`：普通异常、未知错误、运行中取消、超时、协议异常、账本损坏、投递冲突或缺回执等仍无法确定；不自动重发。相同 requestId 始终返回原记录，重启也不重放。

目前仅有合成 reader、注入的可信 native runner 和桌面 smoke 流程验证；没有用此路径向真实联系人发送图片或文件，也没有完成不同 UI 缩放、图片格式、文件种类及实际客户端重编码行为的外发验收。
